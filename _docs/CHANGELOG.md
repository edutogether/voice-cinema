## 스플래시 마이크 이모지 원복 (2026-09-10, 대표 최종)

앞 항목에서 `🎤`로 바꾼 것을 **되돌렸다.** 대표가 아이폰 실기기에서 보고 "원래 은색
세우는 마이크가 더 낫다"고 판단을 바꿨다. 스플래시 로고는 다시 `🎙️`(U+1F399 U+FE0F)이고
파비콘과 같은 글자가 됐다.

**남는 교훈** — 이모지는 기기마다 글리프가 다르다. 개발 PC(Segoe UI Emoji)에서 본 모양으로
고르면 실제 사용자가 보는 것과 다를 수 있다. 화면에 나오는 이모지를 바꿀 때는 **실기기
확인을 거친 뒤에** 확정한다. 어두워 보이던 원인 진단(배경이 아니라 글리프 몸통) 자체는
그대로 유효하고, 손볼 여지는 이모지가 아니라 그림자·배경 대비 쪽에 남아 있다.

스플래시 로고를 `🎙️`(U+1F399 U+FE0F)에서 `🎤`(U+1F3A4) 한 글자로 바꿨다. 어두워 보이던 것은
배경이 아니라 U+1F399 글리프의 몸통 자체였고, 실제로 스플래시 배경에는 어두운 판이 없다.

않았다 — PC 72px / 375px 48px, `drop-shadow(rgba(233,196,106,0.35) 0 10px 24px)`, `splashPop`이
그대로임을 브라우저 계산값으로 확인했다. 파비콘은 `🎙️`로 남으며, (가)를 고른다는 것이
그 차이를 받아들인다는 뜻이다.

## 도메인 이전과 실기기 다듬기 (2026-09-09, 대표 지시)

**도메인 이전** — 정본 주소가 `voice-cinema.web.app`에서 **`voice.edutogether.kr`**로 바뀌었다.
CSP에는 자기 도메인이 한 줄도 없어 손댈 것이 없었고, QR은 앱 주소가 아니라 Storage 공개 URL을
담으며, Auth는 쓰지 않아 승인 도메인 항목도 없었다. 실제로 필요한 것은 두 가지뿐이었다 —
콘솔의 reCAPTCHA 승인 도메인(대표)과 CORS 허용 출처(코드). 기존 `edutogether.kr` 정규식이 `$`로
끝나 **서브도메인을 매치하지 않는 것**을 실측으로 확인해 별도 항목을 넣었고, 허용/차단 경계를
`functions/test/allowed-origins.test.js`로 고정했다(앵커·점 이스케이프까지). 옛 주소는 살려둔다 —
그게 롤백 경로다. 자세한 경위는 `_docs/intents/2026-09-09-domain-migration/intent.md`.

**서비스워커 두 건.** ①프리캐시 목록에 든 문서(`/privacy.html`)가 캐시 우선 분기에 먼저 걸려
**네트워크를 아예 보지 않았다** — 새로 배포해도 옛 화면이 계속 나왔다. 탐색 요청 분기를 앞으로
옮겼다. ②새 서비스워커가 제어권을 잡을 때 앱이 스스로 새로고침하고 있었다 — 부스에서 아이가
녹음 중이면 작업이 통째로 날아간다. 없앴고, 대신 홈 화면에 **"새 버전이 있어요" 알림**을 띄워
사람이 누를 때만 새로고침한다.

**폰트를 자체 호스팅으로.** 이 앱에는 웹폰트가 아예 없었다 — `font-family`에 이름만 적혀 있어
Pretendard가 설치된 기기와 없는 기기가 다른 글꼴로 보였다. 빌드가 화면에 나올 글자만 남겨
**3.9MB → 328KB(8.4%)**로 서브셋한다. 처음에는 빌드 산출물만 훑었는데 번들러가 한글을 유니코드
이스케이프로 내보내 **140자가 빠졌고**, fontTools로 서브셋 cmap을 직접 읽어 잡았다.

**모바일 카드.** 미리보기와 강조가 마우스 호버로만 켜져 터치 기기에서는 여섯 장이 정지 이미지였다.
여섯 장 전부 음소거로 재생하고, 강조는 누르고 있는 동안(`:active`)에 건다 — PC의 `:hover` 선언을
그대로 나눠 쓴다. 카카오톡처럼 **동시 재생을 하나로 제한하는 환경**은 `play()`가 거듭 거부되는
사실로 판별해 한 장씩 돌려 재생한다(브라우저 이름을 쓰지 않는다).

**인앱 브라우저에서만 다르던 것.** `color-mix()`를 옛 WebView가 모르면 그 선언 전체를 무시해
누를 때 강조가 통째로 사라졌다 — 색을 미리 계산해 넘긴다. `-webkit-font-smoothing: antialiased`는
애플 기기에서만 글자를 얇게 그려, 글꼴이 같아진 뒤에는 굵기만 달라 보이는 원인이라 뺐다.

**화면 다듬기** — 제목·부제 위치와 크기, 개인정보처리방침 화면 전면 교체(Be a Googler 양식,
밝은 화면)와 문구 4건, 자동삭제 예약을 방침이 약속한 자정으로 맞춘 것(고지문과 예약 시각을
`test/contract.test.js`가 대조한다).

**실기기에서만 드러난 것들.** 대표가 카카오톡·아이폰으로 확인하며 잡아준 것들이다.
스플래시가 한 프레임 번쩍이고 사라지던 것("한 탭에 한 번만" 층을 얹었더니 정적 마크업이
이미 그려진 뒤에 JS가 지워서 생겼다 — 그 층을 걷어냈다), 터치에서 `:hover`가 붙어 방침
링크가 금색으로 굳던 것(호버 규칙을 마우스 있는 기기로 한정), 누를 때 강조가 "큰 네모"로
보이던 것(모양이 아니라 크기 문제였다 — 카드 반경 24px에 번짐 48px+퍼짐 6px이라 둥근 구간이
빛에 파묻혔다. 16px·퍼짐 없음으로 줄이고 색 덮기도 0.4→0.12로 낮췄다), 그리고 애플 기기에서만
글자가 얇던 것.

**새 버전 알림.** 자동 새로고침을 없앤 뒤로 열어둔 탭이 계속 옛 화면을 보여줘, 고친 것을
확인할 수 없는 상태가 하루 종일 이어졌다(대표의 지적 네 번이 전부 그것이었다). 새 서비스워커가
제어권을 잡으면 홈 화면 오른쪽 아래에 작게 알리고, **누를 때만** 새로고침한다. 이 작업 중
등록 코드를 옮기다 `load` 이벤트가 이미 지난 뒤에 리스너를 다는 회귀를 냈는데, 서비스워커가
아예 안 붙어 오프라인 부팅이 죽는 상태였고 `e2e/offline-boot.spec.js`가 잡았다.

**문서 정리.** `_shared/DOC-STANDARD.md` 기준으로 점검해 한글 파일명을 정리하고, 이미 사실이
아닌 설치 안내(삭제된 `server.js`를 덮어쓰라는 내용)를 `_docs/archive/`로 옮겼다. README의
자동삭제 시각이 옛 값이라 방침·코드·README가 서로 다른 시각을 말하던 것도 고쳤다.

**이날 배운 것 — 흔들리는 테스트는 흔들리는 코드였다.** 간헐적으로 실패하던 테스트 두 개가 각각
진짜 결함이었다: 재생 거부를 한 번만 보고 순환 모드로 굳던 것(부스 태블릿이 한 번 버벅이면 영영
한 장만 돌았을 것), 호버를 벗어난 뒤 재시도가 영상을 되살리던 것. 그리고 **고친 것이 기기에서
확인되지 않던 네 번의 지적은 전부 서비스워커 캐시**였다 — 비공개 탭에서는 처음부터 정상이었다.

## 리액트 + 타입스크립트 전환, GitHub Pages 폐지, 종합감사 (2026-09-08, 대표 지시)

**전환**: 바닐라 JS/HTML(`docs/`가 곧 배포 폴더)에서 **Vite + React 19 + TypeScript**(`src/` → 빌드 산출물 `dist/`)로 프론트를 전면 재작성했다. 목표는 "그대로 옮기기"가 아니라 **"깔끔하게 다시 짜되 동일함을 증명"**이었다.

- **이미 터졌던 버그를 구조적으로 불가능하게**: ①서비스워커 캐시 목록을 손으로 관리하던 구조를 없애고 빌드가 산출물에서 자동 생성하게 했다(`tools/precache-plugin.js`) — 앱 셸·`vendor/`가 목록에서 비면 **빌드가 실패**하고, `CACHE_NAME`을 사람이 올릴 자리도 없다. ②인라인 스크립트를 0개로 만들어 `firebase.json`의 CSP sha256 해시 2개를 삭제했다. ③업로드 타임아웃·`BOOTH_TOKEN`이 클라이언트·서버에서 어긋나면 `test/contract.test.js`가 CI를 떨어뜨린다.
- **전환 중 실측으로 발견해 고친 것**: 서비스워커가 프리캐시 항목을 런타임에 다시 저장하면서 Hosting의 `Vary: Origin` 때문에 **캐시에 있는데도 못 찾는** 상태가 됐다 — 그대로 배포됐으면 오프라인에서 앱이 안 떴다. `ignoreVary: true`로 조회하고 재저장하지 않도록 고쳤고, 그 규칙을 AGENTS.md·개별법에 함정으로 못박았다.
- **동일함의 증명**: 전환 직전 태그(`voice-cinema-freeze-20260908-pre-react`)를 워크트리로 꺼내 옛 앱과 새 앱을 동시에 띄우고 기계 대조했다(`tools/compare-visual.js` = 좌표+computed style 40여 개, `tools/compare-attributes.js` = alt·aria·meta·lang·href·`<video>` 속성·요소 id). **실제 차이 5건**(스플래시가 첫 페인트에 없음, 진행바 표시 단계, 카운트다운 중 문구, 엔진 실패 문구, `.privacylink`/`.chip .e` 값)과 **요소 id 21개 유실**(마크업 20 + 파비콘 link 1 — 커밋 `a960f30`의 제목이 "12개"라고 적은 것은 잘못 센 값이고, 그 커밋 본문의 목록이 정확하다)을 찾아 전부 되돌렸다. 최종: 5개 화면 computed style 차이 0건, 속성 대조 78개 중 차이는 리액트 마운트 지점 `#root` 하나뿐.
- **걷어낸 것**: 리셋 로직 4곳 분산 → 단계(phase) 하나 + effect cleanup, 복붙 4종(진행바 콜백·녹음정지 try/catch 4회·실패 복구·ffmpeg 정리), 취소 토큰 2벌 → 1벌, DOM 직접 조작 118회, 63/60줄 함수 분해, 죽은 코드(`.badge` CSS·`"use strict"`·불가능한 널가드·죽은 eslint 설정).
- **배포 파이프라인**: 배포 폴더가 `dist/`(gitignore 대상)로 바뀌었는데 배포 잡이 프론트를 빌드하지 않아 **빈 폴더를 배포할 뻔한 것**을 배포 직전에 잡아 `npm run build` 단계를 넣었고, 스모크 검증도 "200이면 통과"에서 번들 참조·프리캐시 목록 확인까지로 강화했다.

**GitHub Pages 폐지**: 전환으로 `docs/`가 사라지며 Pages 빌드가 매 push마다 실패했고, 옛 주소는 마지막 성공 빌드(전환 전 앱)를 계속 서빙하고 있었다. 세 안(끄기 / `dist/`를 Pages에도 올리기 / 리다이렉트)을 산정해 올렸고 **대표 지시로 ①끄기로 확정**했다("옛 주소로 오는 사람 살릴 필요 없어. 가장 깔끔하고 완벽한 걸로"). Pages를 비활성화하고, `functions/index.js`의 CORS 허용 목록에서 `edutogether.github.io`를 빼고, 저장소 전체의 `github.io` 서술을 정리했다. **폐지 전 설정은 `build_type: legacy`, `source: master /docs`** — 되살릴 일이 생기면 이 값이 필요하다.

**종합감사(§7)**: 전환 당일의 새 코드를 대상으로 Opus 6개 항목·Sonnet 4개 항목을 각각 별도 호출해 독립 조사했다. 발견된 진짜 결함은 전부 그 라운드 안에서 수정·재검증했다 — 홈으로 나가도 영상·목소리가 계속 재생되던 문제, 첫 설치 시 새로고침이 작업을 날리던 문제, 서비스워커 탐색 폴백의 `ignoreVary` 누락과 실패 응답 캐싱, 배포 폴더에 있던 운영자용 안내문 공개, 영상 초기화 코드 3줄 중복, 합성 실패 경로 미검증. 자세한 내용과 점수는 그날 팀장 보고에 있다.

대표님 질문("하루 2000명 돌려도 괜찮냐")에 실제로 실측했다 — Playwright로 10개 병렬 워커가 진짜 프로덕션 Firebase Functions/Storage에 **2000건을 실제로 업로드**(파일명에 `stress_` 접두사 임시로 붙여 실제 학생 업로드와 분리, 끝나고 전부 삭제 확인). 결과: **1989/2000(99.45%) 성공**, 총 52.5분, 레이트리밋 429는 **0건**(분당 60건 상향이 정상 작동 확인). 11건 실패는 거의 전부 같은 반복 지점(i≈121)에 몰려있어 테스트 하네스/네트워크의 일시적 blip으로 판단(시스템적 용량 문제 아님).

- **L1(확장성, −3점 사유였음) — 클립/엔진 캐시헤더 추가**: `firebase.json`의 헤더 블록이 `clips/**`를 다루지 않아 13MB 클립이 Hosting 기본 1시간 캐시에만 의존했다(장르 바꿀 때마다·1시간마다 행사장 와이파이로 재요청). `clips/**`·`vendor/**`에 `Cache-Control: public, max-age=86400`(1일)을 추가했다 — `docs/sw.js`가 clips를 캐시 대상에서 뺀 이유("행사 전 교체될 수 있어서")는 2026-09-01 클립 확정으로 이미 만료됐지만, SW precache 목록 변경까지는 이번엔 하지 않고(엔진 파일과 성격이 다름 — 클립은 재인코딩 가능성이 남아 있어 HTTP 캐시 갱신 여지를 남겨둠) HTTP 헤더만으로 충분한 개선을 확보했다.

### 배포 직후 실사용에서 발견된 회귀 — 썸네일 `loading="lazy"` 제거 (2026-09-03)
2차 개편 배포 직후, 대표 본인이 실제 화면에서 6개 카드 썸네일이 전부 까맣게 보인다고 확인했다(팀장 세션 경유 보고). 이 세션의 내장 샌드박스 브라우저와 curl로는 몇 차례 재확인해도 재현되지 않았지만("이 세션에서는 안 보임"을 근거로 넘기지 않고), 실사용자가 실제로 겪은 문제이므로 원인을 계속 추적했다.

**원인으로 지목하고 제거한 것**: `docs/app.js`의 `<img class="thumb">`에 걸어뒀던 `loading="lazy"`. 이 화면은 절대 스크롤되지 않는 단일 뷰포트 그리드인데, 이미지의 뷰포트 교차 판정이 그리드가 `aspect-ratio`로 최종 레이아웃을 확정하기 **이전** 시점의 크기로 잘못 계산되면(레이아웃이 아직 0×0이거나 화면 밖으로 계산됨), 다시 재평가할 스크롤 이벤트 자체가 이 화면엔 없어서 영영 안 불러와질 수 있는 알려진 브라우저 동작 패턴과 정확히 들어맞는다. 썸네일 6장을 합쳐도 130KB 수준이라 애초에 지연로딩으로 얻을 이점이 없었던 것도 감안해, `loading="lazy"`를 완전히 제거하고 즉시 로딩으로 바꿨다.

**정직하게 남기는 불확실성**: 이 세션의 도구(내장 샌드박스 브라우저, curl)로는 원래 증상 자체를 한 번도 재현하지 못했다 — 그래서 이 수정이 100% 확실한 근본 원인이라고 단정하지 않는다. 다만 (1) 증상(정적 뷰포트에서 이미지가 로드 자체가 안 됨)과 이 알려진 lazy-loading 실패 패턴이 정확히 일치하고, (2) 이 화면에서 지연로딩이 애초에 불필요했으므로, 되돌릴 이유 없는 안전한 수정이다.

### 진짜 근본 원인을 실측으로 찾음 — 서비스워커 stale-cache 폴백 (2026-09-03, 같은 날 후속)
위 `loading="lazy"` 제거를 배포한 직후 이 세션이 직접 재검증하다가, **이 세션 스스로도 같은 증상을 실측으로 재현**했다: `fetch('./app.js', {cache:'no-store'})`로 HTTP 캐시를 완전히 우회해 받아와도 응답 본문에 `loading="lazy"`가 그대로 남아있었다(방금 막 지운 배포 이후인데도). 원인은 `docs/sw.js`의 app-shell fetch 핸들러였다 — network-first이긴 하지만, 그 순간 네트워크 요청이 (일시적 실패 등) 어떤 이유로든 실패하면 `.catch()`가 곧바로 이 서비스워커가 **맨 처음 설치되던 시점**의 아주 오래된 캐시로 조용히 폴백한다. `cache:'no-store'`를 지정해도 서비스워커의 `fetch(event.request)`가 그 요청 객체를 그대로 넘겨받아 처리하므로 무력화되지 않았다. 즉 한동안 이 사이트를 열어본 적 있는 기기(대표님 포함)는, 재방문 시 네트워크가 아주 잠깐만 불안정해도 몇 주 전 버전의 app.js를 계속 받게 될 수 있는 구조였다 — 이번 UI 개편과 무관하게 이 서비스워커가 처음 배포된 이후 계속 존재했던 잠재 결함이다.

**수정**: 
1. `docs/sw.js`의 `CACHE_NAME`을 `v2`→`v3`로 올렸다 — 서비스워커 스크립트 자체의 바이트가 바뀌어야 브라우저가 "새 버전이 있다"고 인식해 install/activate를 다시 돌리므로(그래야 옛 캐시가 실제로 지워진다), 오래 재방문 안 한 기기까지 포함해 이번 기회에 강제로 전부 초기화한다.
2. `docs/app.js`의 서비스워커 등록부에 `controllerchange` 리스너를 추가해, 새 서비스워커가 제어권을 넘겨받는 순간 자동으로 한 번 새로고침하도록 했다(세션당 1회, 무한루프 방지) — 안 그러면 새 서비스워커가 활성화돼도 이미 열려있던 탭은 수동으로 두 번 새로고침해야 반영되는 표준 서비스워커 동작 때문에 사용자가 여전히 옛 화면을 보게 된다.

lint/유닛 21/21/라이브 E2E 8/8 재검증 후 배포, 배포 후 이 세션이 다시 `fetch(..., {cache:'no-store'})`로 최신 app.js가 실제로 오는지까지 재확인했다. **이 결함은 오늘 UI 개편으로 새로 생긴 게 아니라, 서비스워커를 도입한 이후(2026-08-27, 테스트/린트/캐싱 섹션 참고) 쭉 존재했을 잠재 결함이었고, 이번에 실사용 중 우연히 크게 드러난 것**이라는 점을 남겨둔다 — 앞으로 app-shell(index.html/app.js/logic.js) 내용을 바꿀 때마다 `CACHE_NAME`을 올리는 습관이 필요하다.

팀장 세션이 재확인해 "6개 카드 전부 정상"이라고 확정했다.

## 홈 화면 개편 3차 (2026-09-03, 같은 날 재차 — 대표 라이브 재확인 후 추가 지시 6건)

- **재검증**: lint 무결점, 유닛 21/21, 라이브 Playwright E2E 8/8, Claude in Chrome으로 데스크탑·모바일 뷰포트 직접 스크린샷 확인.

## 홈 화면 개편 4차 (2026-09-03, 같은 날 세 번째 — 정정 2건 + 스플래시 버벅임)

## 업로드 타임아웃 60초→110초, 재시도 1→2회 (2026-09-06, 대표 지시)
Bumm님 지시로 (1) 완성 mp4 용량 최적화(720p 재인코딩 제안, 아직 미적용 — 실제 ffmpeg.wasm 인코딩 속도 확인 전이라 보류 중) (2) 열악한 네트워크에서 업로드 타임아웃 실측을 진행했다. 실측 과정에서 중요한 발견 두 가지가 있었다:

- **타임아웃이 클라이언트·서버 두 곳에 각각 존재했고 둘 다 60초로 방치돼 있었다**: `docs/app.js`의 `AbortController`(클라이언트)뿐 아니라 `functions/index.js`의 `onRequest({ timeoutSeconds: 60 })`(Cloud Run 기반 서버 측)도 60초였다. 서버 쪽은 클라이언트가 얼마나 기다리도록 설정했든 상관없이 그 시간이 지나면(느린 업로드를 받는 도중이라도) 먼저 연결을 끊는다 — 클라이언트만 늘리고 서버를 안 늘리면 아무 효과가 없다. `docs/app.js`의 API_BASE가 Firebase Hosting rewrite를 거치지 않고 Cloud Functions URL을 직접 호출하므로 Hosting 레이어의 별도 타임아웃은 해당 없음을 확인했다.
- **크롬 DevTools 표준 프리셋(Fast 3G: 업로드 0.75Mbps·지연 560ms / Slow 3G: 0.4Mbps·지연 2000ms)으로 로컬에서 실제 대역폭 제한을 재현해 실측**(이 세션 툴로는 DevTools 자체를 직접 제어할 수 없어, 실제 `/upload`와 동일한 요청 크기·base64 인코딩 오버헤드까지 반영한 로컬 스로틀 재현으로 대체) — 720p 재인코딩 제안(평균 5.91MB, base64 포함 전송량 약 7.88MB) 기준으로 **Fast 3G 93.9초, Slow 3G 171.0초**가 나왔다. 대표 설계 목표("Fast 3G는 성공, Slow 3G는 억지로 성공시키지 말고 적당한 시간 안에 실패 후 로컬 폴백")에 맞춰 **110초**로 정했다 — Fast 3G는 여유(~16초) 있게 성공하고, Slow 3G는 171초까지 안 기다리고 110초에서 끊겨 폴백으로 넘어간다.

**적용(클라이언트+서버 동시)**:
- `docs/app.js`: `UPLOAD_TIMEOUT_MS = 110000` 상수 추가, `uploadOnce()`의 `AbortController` 타임아웃에 사용. `uploadToCloud()`를 재시도 1회→2회(최대 3회 시도)로 변경 — `shouldRetryUpload()`가 타임아웃(`AbortError`)은 이미 재시도 대상에서 제외해두므로, Slow 3G처럼 타임아웃으로 끝나는 경우는 재시도 횟수와 무관하게 1회 만에 바로 폴백으로 넘어간다(늘어난 재시도는 순간적 끊김 등 타임아웃이 아닌 실패에만 적용).
- `functions/index.js`: `voiceCinema`의 `onRequest({ timeoutSeconds: 110 })`로 클라이언트와 동일하게 맞춤.
- `docs/sw.js`: `CACHE_NAME` v8→v9(app.js 내용 변경에 맞춰 서비스워커 캐시 강제 갱신).

lint 무결점, 유닛 21/21, 라이브 Playwright E2E 8/8(포트 4321이 이번엔 비어 있어 별도 우회 불필요) 재검증 통과.

**720p 인코딩(용량 축소) — 적용 완료(2026-09-06, 같은 날 후속)**: 처음 제안한 방식(브라우저 `mergeClip()`에서 매 학생 요청마다 `-c:v copy` 대신 `libx264`로 720p 재인코딩)은 실제 브라우저(Claude in Chrome)에서 실측한 결과 **클립당 36.6~44.2초(평균 39.3초)**가 걸려 채택하지 않았다 — "영화를 만들고 있어요…" 대기시간이 거의 즉시(93~173ms)에서 40초 가까이 늘어나는 건 부스 현장에서 감당하기 어렵다고 판단했다.

**대신 채택한 방법**: 매 요청마다 다시 인코딩해야 하는 건 학생 음성(오디오)뿐이고, 영상 부분(6개 장르 클립)은 애초에 누구에게나 항상 똑같다는 점에 착안 — **정적 원본 클립 파일(`docs/clips/*.mp4`) 자체를 로컬에서 미리 한 번만 720p로 재인코딩**해 교체하고, 브라우저 쪽 실시간 파이프라인(`mergeClip()`)은 `-c:v copy` 그대로 안 건드렸다. 이러면 매 학생 업로드마다 인코딩 시간 증가가 전혀 없으면서(계속 93~173ms 수준) 완성본 크기만 줄어든다.

- **인코딩 설정**: `-vf scale=1280:720 -c:v libx264 -profile:v high -preset veryfast -b:v 5000k -maxrate 5500k -bufsize 10000k -pix_fmt yuv420p -c:a copy -movflags +faststart`. 오디오는 원본 클립의 AAC 트랙을 `-c:a copy`로 그대로 보존했다 — `mergeClip()`이 최종 결과물에선 이 오디오를 안 쓰지만(`-map 1:a:0`으로 학생 음성만 씀), 스튜디오 화면의 **미리보기**(`togglePreview()`가 `v.muted=false`로 재생)에서는 실제로 학생이 이 오디오를 듣게 되므로 무음이나 다른 소리로 바꾸면 안 된다 — 실제로 재인코딩 전후 오디오 트랙을 추출해 MD5 해시까지 비교해 바이트 단위로 동일함을 확인했다.
- **실측 결과(6개 장르 전부, 실제 프로덕션 `mergeClip()` 파이프라인 재현 기준)**: 5.66MB(시트콤)~6.14MB(호러), 평균 5.90MB — 요청한 5~8MB 범위 안에 여유 있게 들어온다.
- **썸네일 재생성**: `docs/clips/thumbs/*.jpg`도 새 720p 클립에서 다시 추출했다(화질 차이는 육안상 없음, 프레임 캡처 방식은 동일).
- **화질 확인**: 재인코딩 전후 같은 시점(5초) 프레임을 나란히 캡처해 육안 비교 — 차이를 거의 느끼기 어려웠다(이전 실측 때 보낸 캡처와 동일 설정·결과).
- **재검증**: lint 무결점, 유닛 21/21, 라이브 Playwright E2E 8/8. `docs/sw.js`의 `CACHE_NAME`을 v9→v10으로 올렸다(클립 내용이 바뀌었는데 파일명은 그대로라, 이미 방문한 기기의 서비스워커 캐시가 옛 1080p 바이트를 계속 들고 있을 수 있어서).
- **알아둘 점**: `firebase.json`의 `clips/**` 캐시 헤더(`max-age=86400`, 1일)는 서비스워커와 별개인 브라우저 자체 HTTP 캐시라 이번 배포로 즉시 무효화되지 않는다 — 배포 직전에 이미 그 클립을 받아본 적 있는 기기는 최대 하루 동안 이전 1080p 파일을 계속 쓸 수 있다(하루 지나면 자동으로 새 파일을 받는다). 기능상 문제(재생 실패 등)는 없고 단순히 그 기기만 용량 축소 효과를 하루 늦게 보는 정도라 별도 조치는 하지 않았다.
