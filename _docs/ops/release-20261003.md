- 실제 마이크 오류 분류, 녹음·다시 듣기·재녹음·브라우저 합성·저장, 브라우저 방문 기록.

## 검토와 수정

초기 전체 E2E는 123개 중 116개 통과, 7개 실패였다. 원인을 확인한 뒤 다음을 수정했다.

1. 방문 기록 검사가 로컬 샘플 쿼리로 들어가 실제 MediaRecorder·업로드를 실행하지 않았다. 운영 경로로 검사하도록 수정했다.
2. PC 카드 검사가 과거의 호버 전용 재생을 기대했다. 승인된 중앙 무음 자동재생과 호버 이탈 뒤 한 장 재생을 검사한다.
3. 녹음실 배치 검사가 상위 요소의 애니메이션만 기다렸다. 실제 확대 요소의 완료를 기다린다.
4. 하단 카드 재진입 뒤 같은 카드 안의 포인터 이동에서도 선택을 갱신한다. 기존 사진·글씨·빈 영역 클릭 회귀를 유지한다.
5. 취약한 전이 의존성만 갱신했다. 서버 `@grpc/grpc-js` 1.14.4→1.14.5, `brace-expansion` 2.1.4→2.1.7, 프론트 개발 의존성의 `brace-expansion`도 허용 범위에서 갱신했다. 강제 갱신·직접 의존성 변경은 없다.
6. 첫 PR CI는 동작 검사 122개 통과·1개 실패였다. Linux 합성기의 완전 노출 비율이 `0.99999994`로 반환되어 정확히 1을 요구한 검사에 걸렸다. 장면 이동 완료를 확인하고 제목의 네 경계가 화면과 클리핑 영역 안에 있는지 직접 검사하도록 바꿨다. 가시 비율 기준 완화나 자동 재시도는 추가하지 않았다.

상태·자원 정리, 샘플 모드의 운영 차단, 원본/합성 경로, 서버 인증·레이트리밋·CORS·삭제 경계,
서비스워커 갱신/오프라인, 키보드·모바일 배치를 검토했다. 보안 헤더·Storage deny·서버 업로드 검사 순서는 유지한다.

```powershell

$env:VOICE_VISUAL_BASELINE='1'

Remove-Item Env:VOICE_VISUAL_BASELINE

```

Windows 기준선은 `e2e/release-baseline.spec.js-snapshots/`의 PNG 6개와 위치·글꼴·조작 의미 JSON 6개다.
홈 PC/휴대폰, 녹음실 PC/휴대폰, 실제 녹음 완료, 실제 합성 후 QR 결과를 포함한다.
현재 승인된 디자인으로 생성 후 갱신 옵션 없이 다시 비교한다. 움직이는 영상·시계만 같은 순간에 고정하며 배치·색·글꼴은 바꾸지 않는다.
정지 기준선 외 일반 동작·모션은 기존 E2E가 별도로 검사한다. Linux CI에서 Windows 픽셀을 대신 검사했다고 기록하지 않는다.

## 검증 범위와 한계

- 최종 로컬 검사: lint·타입 검사·빌드 통과, 단위/서버 검사 61개 통과, 전체 E2E와 Windows 화면 기준선 129개 통과(6.4분).
- Windows 기준선 6개를 갱신 없이 재비교해 통과했다. 제목 배경색을 검사 안에서 바꾼 음성 대조군은 스크린샷 불일치와 종료 코드 1로 실패하여 감지 동작을 확인했다.
- 동시 브라우저 6개에서 장면 왕복 36회, 실제 녹음·MP4 합성·QR 결과 6회가 22초에 완료됐다. 화면 오류 0건이다. 루트/Functions 의존성 감사는 개발 의존성 포함 취약점 0건이다.
- 로컬 환경: Windows, Node 24.18.0, npm 12.0.2, Playwright Chromium. 운영 CI/Functions는 Node 22다.
- 로컬 업로드 방어 부하: 같은 IP에서 20개 동시 연결로 2,000건. 60건 인증 거부(403), 1,940건 레이트리밋(429), 성공 우회·5xx 0건.
- 브라우저 부하는 실제 가짜 마이크 녹음·ffmpeg.wasm 합성을 사용한다. Storage 요청만 가로채 파일 유효성과 QR 전달을 검사한다.
- 운영 Storage에 참가자 데이터나 시험 데이터를 쓰지 않는다. 실기기 마이크·현장 Wi-Fi·운영 업로드 용량의 실측 결과로 확대 해석하지 않는다.
- 이전 별도 작업의 `.codex/config.toml`은 이번 제품 커밋에 포함하지 않는다.

## 배포 확인·되돌리기

PR 검사 → 승인된 PR 병합 → 해당 병합 커밋의 CI → Deploy Backend 성공 → 운영 번들/서비스워커·화면 확인 → 프리즈 태그 순서다.
운영 확인 결과와 최종 SHA는 태그 설명 및 공식 인계 원장에 기록한다.
되돌릴 때는 필요한 변경을 작업 가지에서 revert하고 PR·CI로 배포한다. 기존 프리즈 태그를 이동하거나 운영 파일을 직접 덮어쓰지 않는다.
