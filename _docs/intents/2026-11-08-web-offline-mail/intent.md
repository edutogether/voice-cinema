# 웹(크롬)에서도 인터넷이 끊기면 인솔 선생님 메일 칸을 띄운다

## 문제

설치판은 QR을 만들지 못하면 이름 또는 별명과 인솔 선생님 메일을 받아 두었다가, 인터넷이 돌아오면 올리고 메일을 보낸다(11/8 라이브 `0090e49`).
웹은 지금도 «이 기기에 저장»으로 간다. 파일이 부스 노트북 다운로드 폴더에 남고, 학생에게 전하고 지우는 일이 모두 사람 몫이다.
Bumm님 결정: 웹도 끊기면 같은 메일 칸을 띄운다.

## 원하는 결과

- 크롬(웹)에서 QR을 만들지 못하면 설치판과 같은 메일 칸이 뜬다: 입력 → 주소 확인 → 대기.
- 영상 · 이름 · 주소는 그 기기 크롬의 사이트 저장소(IndexedDB)에 맡긴다.
- 인터넷이 돌아오면 저절로 올리고, 메일을 보내고(선생님당 한 통), 맡긴 것을 지운다.
- 대기 화면에 조건 두 가지를 짧게 적는다.
  - ① 인터넷이 돌아올 때 이 창이 열려 있어야 보내진다.
  - ② 크롬 기록(사이트 데이터)을 지우면 보내기 전 영화도 지워진다.
- 첫 화면의 «메일 대기 N건» 단추와 목록(다시 보내기 · 지우기)도 웹에 같이 둔다. 운영자가 남은 건을 보고 처리할 수 있어야 한다.

## 영향받는 사용자 · 시스템

- 웹을 쓰는 모든 기기. 부스 노트북, 그리고 업로드에 실패한 휴대폰도 같은 화면이 된다.
- 서버(`/mail`)는 그대로다. 설치판만 받는 검사가 없어 웹 요청도 같은 문 검사(부스 토큰 · App Check · 분당 20)를 거친다.
- 설치판은 그대로다. 다리(`window.vcDesktop.mail`)가 있으면 지금처럼 암호화 파일 보관을 쓴다.
- `privacy.html`: «설치판에서만 받는다»를 사실대로 고친다.

## 제약

- 새 서버 · 새 비용 · 새 키를 만들지 않는다. `/mail`과 설치판 화면을 그대로 쓴다.
- 동의 체크 · 동의 화면 · 긴 고지를 넣지 않는다(동의는 교육청이 맡는다).
- 로그 · 콘솔에 메일 주소와 이름을 남기지 않는다. 다음 사람에게 이전 주소 · 이름이 뜨지 않는다(입력 칸 자동 완성 끔 · 화면 상태에만 둠, 설치판과 같다).
- 실제 발송 시험은 테스트 주소로만 한다. 받는 주소는 기록 · 커밋 · 캡처에 남기지 않는다.
- 배포는 «배포 직전 한 줄» → 팀장 OK → master push → CI로만.

## 설계

- **보관(웹)**: `src/lib/mailStoreWeb.ts`가 설치판 다리와 같은 다섯 가지(`add` · `list` · `video` · `update` · `remove`)를 IndexedDB로 낸다.
  - 데이터베이스 `voice-cinema-mail`에 두 칸을 둔다: 정보(`items`)와 영상(`videos`, Blob).
  - 한 건은 한 거래(transaction)로 쓴다. 도중에 닫혀도 반쪽 건이 남지 않는다.
  - 2026-12-01 00:00(KST) 이후 목록을 읽으면 전부 지운다. 서버의 자동 삭제 시각(`CUTOFF_DATE`)과 같고, 계약 검사가 대조한다.
- **암호화하지 않는다**: 웹에서 암호화하려면 열쇠도 같은 사이트 저장소에 둘 수밖에 없다. 그러면 디스크를 읽는 사람에게서 지켜 주는 것이 없다. 방침에는 «이 브라우저의 사이트 저장소에 보관»이라고 사실대로 적는다(설치판만 «암호화»).
- **언제 메일 칸인가**: 설치판과 같다. 인터넷이 없다고 나오거나 올리기가 실패하면 메일 칸으로 간다.
  - 부스 KT EGG가 LTE만 끊기면 노트북은 여전히 «연결됨»이다. 그래서 실패도 같은 끊김으로 본다.
  - 이 기기에 저장으로 가는 경우:
    - 미리보기 채널 주소(서버가 받지 않는다)
    - 브라우저 저장소를 쓸 수 없을 때
    - 맡기기가 실패할 때
- **보내기**: 이 사이트가 열려 있는 동안 화면과 관계없이 돈다.
  - 15초마다 하고, 인터넷이 돌아오는 신호(`online`) 때 전부 다시 시도한다(설치판과 같은 `mailDelivery.ts`).
  - 창(탭)이 여러 개면 한 창만 보낸다(Web Locks). 같은 영화를 두 번 올리거나 메일이 두 통 가지 않게 한다.
- **재시도**: 설치판과 같다. 30초부터 두 배씩 5분까지, 8번 실패하면 «보내지 못함»으로 두고 운영자가 «다시 보내기»를 누른다.
- **삭제**:
  - 보내면 바로 지운다.
  - 운영자가 «지우기»를 누르면 지운다.
  - 12/1 00:00 이후 이 사이트를 처음 열 때 지운다.
  - 크롬 사이트 데이터를 지우면 함께 지워진다.

## 시험

- 유닛: 맡기는 규칙(지울 때), 대기열 규칙, 주소 규칙(설치판 것 그대로).
- E2E(진짜 Chromium · 가짜 마이크 · 업로드 · 메일 가로챔):
  - 끊김 → 입력 → 확인 → 대기 → `online` → 올림 → 메일 → 지움
  - 올리기 실패 → 메일 칸
  - 새로고침해도 남음
  - 창 두 개에서 메일 한 통
  - 12/1 뒤 지움
  - 저장소를 쓸 수 없으면 기기 저장
  - 미리보기 주소는 기기 저장
- 실제 발송: reCAPTCHA 키가 `voice.edutogether.kr` · `voice-cinema.web.app`만 허용해 `localhost`에서는 App Check가 통과하지 않는다.
  - 그래서 이 빌드를 정본 주소 그대로 띄운다. 설치판이 하는 방식에서 다리만 뺀 창이다.
  - 자동화 없이 띄워 끊김 흉내 → 더빙 → 메일 칸 → 연결 → 올림 · 메일 · 지움까지 본다.
  - 메일은 테스트 주소로 받고 도착을 확인한다.
- 캡처: PC 2560 원본으로 단계마다 따로 찍는다. 휴대폰 · 패드 크기는 조사 도구로 메일 칸이 넘치거나 가리지 않는지 본다.

## 확인한 것

- **E2E** `e2e/web-mail.spec.js` 5개: 끊김 → 메일 칸 → 맡김(IndexedDB 1건 · 영상 1개) → `online` → 올림 1번 · 메일 1통 → 지움(0 · 0) · 새로고침 뒤 이어서 · 두 창에서 한 번만 · 12/1 00:00 전후 · 저장소 막힘 → 기기 저장.
  Web Locks를 빼면 «두 창»이 올리기 2번 · 메일 2통으로 빨간불이다.
- **실제 발송에서 결함 둘을 찾았다**(정본 주소로 띄운 시험 창, 11/8 오후) — 둘 다 설치판에도 있다.
  - ① **끊긴 채 연 창은 인터넷이 돌아와도 App Check 토큰을 받지 못했다.** SDK가 넣은 reCAPTCHA 스크립트가 실패한 채 남아 토큰 교환이 0번이었고, 업로드가 401(«App Check 토큰 없음») 네 번 뒤
    대기에 남았다(함수 기록 07:33~07:34Z). `upload.ts`가 App Check를 켜기 전에 스크립트를 직접 받고, 실패하면 흔적을 지워 다음 요청 때 다시 받게 했다.
    고친 뒤 같은 길로 reCAPTCHA 200 · App Check 교환 200 · 업로드 200. `upload-appcheck-wait.spec.js` 둘째 시험이 고정한다(셋으로 일부러 되돌려 빨간불).
  - ② **`/mail`이 진짜 영화 주소를 400으로 거절했다**(«영화 링크가 올바르지 않습니다», 두 번). 업로드는 `…/dubs%2F…`를 돌려주는데 검사는 `/dubs/`만 받았다 — 시험이 전부 «/» 그대로인 가짜 주소였다.
    `functions/mail.js`가 풀어서 보게 했다. 진짜 `publicUrl()` 주소로 시험을 더했다(옛 검사로 빨간불 2개). 이 수정은 functions 배포 뒤에 효력이 있다.
- **조사 도구**: 휴대폰 5 · 태블릿 2 · PC 3 크기에서 메일 칸 · 주소 확인 · 대기 · 완성 40화면 결함 0, 실제 업로드 0(`/mail`도 가로챔). 그림을 눈으로 봤다 — 낮은 휴대폰(375×553)은 «보내기»까지 스크롤한다.
- 실제 시험 창의 캡처(2560×1305 원본): 01 메일 칸 · 02 주소 확인 · 03 대기(조건 두 줄) · 04 첫 화면 «메일 대기 1건» · 05 목록. 받는 주소가 보이는 장은 가렸다.
