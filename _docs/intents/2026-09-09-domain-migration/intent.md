# 정본 주소를 voice-cinema.web.app에서 voice.edutogether.kr로 옮긴다

## 문제

지금 정본 주소가 `https://voice-cinema.web.app`이다. Firebase가 준 기본 도메인이라
같이교육 소속임이 주소에 드러나지 않고, 다른 앱들과 주소 체계가 따로 논다. 대표가
`voice.edutogether.kr`로 확정했다(2026-09-09).

문제는 **시점**이다. 행사일이 2026-11-14이고 **11-07부터 배포 동결**이다. 도메인 전환은
이 앱에서 단순한 주소 변경이 아니다 — 아래 "영향" 참고.

## 원하는 결과

- `https://voice.edutogether.kr`로 접속했을 때 지금과 똑같이 동작한다 — 앱 로드, 녹음,
  합성, 업로드, QR 전달, 오프라인 부팅까지 전부.
- **전환 도중 서비스가 끊기는 구간이 없다.**
- 옛 주소 `voice-cinema.web.app`도 계속 살아 있어, 문제가 생기면 **링크만 되돌려**
  즉시 복구된다.
- 동결(11-07) 전에 새 주소에서 며칠간 실사용 관찰이 끝나 있다.

## 영향받는 사용자·시스템

조사 결과(2026-09-09, 실행 없이 사실만 수집), 항목별로 갈린다.

### 손댈 것이 없는 것 — 조사로 확인함

- **CSP** — `firebase.json`의 CSP에 **자기 도메인이 등장하는 자리가 하나도 없다.**
  전부 `'self'`(오리진 상대) 아니면 제3자 도메인이다. `Permissions-Policy: microphone=(self)`도
  오리진 상대다.
- **Firebase Auth 승인 도메인** — 이 앱은 Auth를 아예 쓰지 않는다(`getAuth`/`signIn` 0건).
- **QR** — QR에 앱 주소가 들어가지 않는다. `functions/index.js`가 `file.publicUrl()`을
  반환하고 그게 QR이 되므로 `storage.googleapis.com` 주소다.
- **코드에 하드코딩된 자기 origin** — 없다. `src/main.tsx`는 `window.location.reload()`,
  `tools/sw-template.js`는 `self.location.origin` 비교로 둘 다 오리진 상대다.
- **서비스워커 프리캐시 경로** — 전부 절대 경로(`/vendor/...`)라 도메인에 독립적이다.

### 콘솔에서 대표가 해야 하는 것

- **reCAPTCHA Enterprise 승인 도메인에 `voice.edutogether.kr` 추가** — **1순위.**
  누락되면 App Check 토큰 발급이 실패하고, 이 앱은 토큰 없이도 요청은 보내지만
  **서버가 401로 거부**한다. 결과는 앱이 죽는 게 아니라 **모든 학생이 QR을 못 받고
  "기기에 저장" 폴백으로만 떨어지는 상태**다 — 부스 운영 방식이 통째로 바뀐다.
  (근거: localhost에서 도메인 제한에 걸려 토큰 발급이 실패하는 것을 이미 실측한 이력이 있다.)
- **Firebase Console → Hosting → 커스텀 도메인 추가.**
  **반드시 `voice-cinema` 사이트에 붙여야 한다.** 이 프로젝트에는 Hosting 사이트가 두 개고
  프로젝트 기본 사이트 `inky-voice-cinema`는 **빈 사이트(404)** 다. 잘못 고르면 404가 서빙된다.
- 가비아에 발급받은 A(+TXT) 레코드 등록 → SSL 자동 발급 대기(최대 24시간).
- **인쇄물 PDF 2종에 앱 주소나 QR이 이미지로 박혀 있는지 눈으로 확인.**
  압축 스트림까지 풀어 텍스트를 검색했을 때 나온 URL은 폰트 라이선스 주소뿐이었지만,
  **이미지로 박힌 주소는 그 방법으로 배제할 수 없다.**

### 코드에서 세션이 해야 하는 것

- **CORS 허용 출처 추가** — 기존 `edutogether.kr` 항목은 정규식이 `$`로 끝나
  **서브도메인을 매치하지 않는다**(실측 확인). 별도 항목이 필요하다.
  → **2026-09-09에 선반영 완료**(`510dbe1`). 추가형이라 도메인이 없는 지금 넣어도 무해하고,
  넣어두면 "화면은 뜨는데 업로드만 CORS로 막히는" 구간이 없어진다.
  회귀 테스트도 함께 넣었다(`bc5218e`, `55156fe`).
- **자기 주소 문자열 교체 — 아직 하지 않았다.** 배포 스모크 검증 3곳
  (`.github/workflows/deploy.yml`), 문서 6곳. **도메인이 실제로 붙기 전에 바꾸면 지금
  라이브 검증이 깨진다.**
  ※ `src/config.ts`의 `authDomain: 'inky-voice-cinema.firebaseapp.com'`은 **사이트 주소가
  아니라 Firebase 프로젝트 설정값**이다. 건드리면 안 된다.

### 이 앱 고유의 큰 영향 — 캐시

**CacheStorage는 오리진 단위다.** 도메인이 바뀌면 새 오리진에는 캐시가 완전히 비어 있고,
**부스 기기가 ffmpeg 엔진 31MB를 처음부터 다시 받는다.** 클립(37MB)도 다시 쌓아야 한다.

코드 수정은 필요 없지만, **행사 전 예열이 통째로 무효화된다**는 뜻이다. 이것이 이 전환의
시점을 정하는 핵심 근거다.

## 제약

- **도메인이 실제로 붙기 전에는 CSP·CORS·코드의 주소를 미리 바꾸지 않는다**(대표 지시).
  지금 바꾸면 라이브가 깨진다. — CORS만은 **추가형이라 무해**하다는 판단으로 팀장 승인 후
  선반영했고, 교체형은 전부 보류 중이다.
- **동결 기간(2026-11-07 ~ 11-14)에는 전환하지 않는다.** 전환은 캐시를 통째로 무효화하므로
  동결이 지키려는 것(예열)을 정면으로 깨뜨린다.
- **옛 주소를 죽이지 않는다.** 옛 주소가 살아 있는 것이 곧 롤백 경로다.
  **행사가 끝나기 전에는 허용 목록에서도 빼지 않는다.**
- 커스텀 도메인은 **반드시 `voice-cinema` 사이트에** 붙인다.

## 권장 시점과 근거

**10-31(금) 전후, 늦어도 11-03까지 포털 카드 링크를 교체한다.**

- 동결 시작(11-07)까지 **최소 나흘**의 실사용 관찰을 남긴다. 이 앱은 **배포된 사이트에서만
  드러나는 회귀**를 실제로 겪었다(CSP가 인라인 핸들러를 막아 버튼 8개가 죽음) — 새 도메인에서도
  며칠은 지켜봐야 한다.
- SSL 자동 발급에 최대 24시간이 걸린다.

**예열**은 캘린더 일수가 아니라 작업이다 — 기기 1대당 새 주소를 한 번 열어 엔진 다운로드가
끝날 때까지 두면 된다(빠른 회선에서 1~2분). **예열은 배포가 아니므로 동결 기간에 해도 되고,
오히려 동결 주간이 가장 안전하다** — 그 사이 캐시를 깨뜨릴 배포가 나가지 않기 때문이다.

## 되돌리는 방법

포털 카드 링크를 옛 주소로 되돌리면 **즉시** 복구된다(옛 주소가 죽은 적이 없으므로).
콘솔에서 커스텀 도메인 제거와 DNS 레코드 삭제는 그 뒤에 여유 있게 한다.
**실질 롤백 시간 = 링크 교체 시간.**

## 미결 질문

- **DNS 등록 시점** — `voice.edutogether.kr`은 현재 존재하지 않는다(NXDOMAIN). 대표가 콘솔·가비아
  작업을 언제 하실지에 따라 이후 일정이 전부 밀린다. **이 답이 나오기 전에는 교체형 변경을
  시작하지 않는다.**
- **전환 후 옛 주소를 언제 정리할 것인가** — 행사 전에는 그대로 둔다는 것만 정해졌고, 행사
  이후에 대해서는 정해진 바 없다. `[확인]`
- **인쇄물에 앱 주소가 이미지로 박혀 있는가** — 텍스트 검색으로는 배제하지 못했다. 대표 확인 필요.
- **포털 카드 링크를 누가 언제 교체하는가** — 이 저장소 밖이다. 팀장·Portal 세션 소관.

## 완료 (2026-09-10 확인)

**이전 자체는 끝났다.** `https://voice.edutogether.kr` 200, 인증서 정상, `http`는 301로
`https`에 자동 전환된다. 배포 스모크 검증도 이 주소를 본다. 옛 주소
`voice-cinema.web.app`도 200으로 함께 살아 있다 — 이미 나간 QR과 링크가 죽지 않게
행사 전에는 그대로 둔다.

남은 것은 이전 작업이 아니라 **현장에서 사람이 해야 하는 것**들이라
[`.claude/rules/app.md`](../../../.claude/rules/app.md)의 "남은 것" 절이 들고 있다.

## 이전 직후 상태 (2026-09-09 실측)

**도메인이 붙었고 살아 있다.** 옛 주소도 함께 살아 있어 롤백 경로가 유지된다.

| 확인 | 결과 |
|---|---|
| `voice.edutogether.kr` DNS | `voice-cinema.web.app`의 별칭 → `199.36.158.100` |
| `voice.edutogether.kr` / `voice-cinema.web.app` / `voice-cinema.firebaseapp.com` | 셋 다 **200** |
| 두 주소가 같은 빌드를 서빙하는가 | 같음 (`/assets/main-fNje8WUc.js`) |
| 새 주소의 `sw.js` 프리캐시 | 엔진 포함, 정상 |
| CORS 허용 | 새 출처 허용, 접미사 위조 차단 (배포 직후 실측) |

**App Check도 새 주소에서 통과하는 것을 확인했다.** 이 항목이 위험했던 이유는 실패해도 화면상
사고처럼 보이지 않기 때문이다 — 앱이 뜨고 녹음도 되고 합성도 되는데 업로드만 401로 거부돼
전원 "기기에 저장" 폴백으로 조용히 떨어진다.

curl로는 확인할 수 없다(App Check 토큰은 reCAPTCHA를 통과한 진짜 브라우저에서만 나온다).
그래서 Playwright로 실제 크롬 창을 띄워 새 주소를 열고, 앱이 쓰는 것과 같은 방식으로 토큰을
발급받아 `/upload`에 **본문을 일부러 비운 요청**을 보냈다. 서버가 헤더 검사(레이트리밋 →
`BOOTH_TOKEN` → App Check)를 통과한 요청만 본문을 파싱하므로, 401이면 App Check 실패이고
400이면 통과한 것이다. 저장소에는 아무것도 쓰이지 않는다.

| | 결과 |
|---|---|
| 토큰 발급 | 성공, 961자 |
| `/upload` 응답 | **400 `파일 데이터가 없습니다.`** — 401이 아니므로 App Check 통과 |

**헤드리스로는 판정할 수 없다** — 새 주소와 옛 주소 둘 다 403(`appCheck/throttled`)이 났다.
옛 주소는 실제 브라우저에서 토큰 발급이 확인된 이력이 있으므로 이 403은 도메인 설정이 아니라
자동화 브라우저 때문이다. 대조군을 같이 돌리지 않았으면 새 도메인 설정이 잘못된 것으로
오판할 뻔했다.
